## 1. 游戏规格

### 1.1 术语表（全项目唯一命名标准）

| 本项目术语 | 英文标识符 | 含义 |
|-----------|-----------|------|
| 方块 | `tile` | 5 色游戏组件，每色 20 块，共 100 块 |
| 展台 | `display` / `displays` | 每轮摆放 4 块方块的公共取料位，2 人局共 5 个 |
| 中央池 | `center` | 展台余料的汇集处 |
| 先手标记 | `first_token` | 决定下轮先手的标记物，编码为 `-1` |
| 备料行 | `staging_rows` | 玩家板左侧 5 行，容量 1..5，同行锁定单色 |
| 网格 | `grid` | 玩家板右侧 5×5 结算区 |
| 罚分行 | `penalty_row` | 玩家板底部 7 槽，放置溢出与弃置方块 |
| 弃料盒 | `discard` | 已结算方块的回收处，袋空时倒回袋中 |
| 取料阶段 | `drafting` | 轮内玩家交替取方块的阶段 |
| 结算阶段 | `settling` | 轮末上格计分与罚分的阶段 |

代码、协议、UI 文案一律使用上表标识符；不得出现其他桌游的专有名词。

### 1.2 规格摘要

完整规格（含全部边界判例）见 [01-engine.md](docs/plans/01-engine.md)。

- **人数**：2 人（5 个展台，每展台 4 块）。
- **方块**：5 色（BLUE, YELLOW, RED, BLACK, WHITE）各 20 块，共 100 块；另有 1 枚先手标记。
- **网格色位**：`color(r, c) = (c - r + 5) mod 5`（第 0 行为 蓝黄红黑白，每行右移一位）。
- **备料行**：容量 1..5；每行锁定单色；网格该行已有该色则该行不可选该色。
- **罚分行**：7 槽，罚分 `-1,-1,-2,-2,-2,-3,-3`；溢出方块进弃料盒；总分不低于 0。
- **取料**：从某展台或中央池取走某色全部方块；展台余料入中央池；首个从中央池取料者获得先手标记并置于罚分行；取得的方块放入一条备料行（溢出落罚分行）**或整组直接弃入罚分行**。
- **结算**：满行取 1 块上网格，余料入弃料盒；新方块得分 = 水平连续段长 H（若 H≥2）+ 垂直连续段长 V（若 V≥2），两者皆为 1 时得 1 分。
- **补料**：每轮开始从袋中抽料填展台；袋空则将弃料盒洗回袋中继续；两者皆空则展台不满员照常进行。
- **终局**：结算阶段后任一玩家网格出现完整横行即终局。加分：完整横行 +2/行，完整竖列 +7/列，集齐同色 5 块 +10/色。
- **胜负**：分高者胜；平分比完整横行数；再平则共同获胜。

## 2. 系统架构与技术栈

```
+------------------------------------------------------------------+
|                    Frontend (Vite + React + TS)                  |
|  - Tailwind CSS，DOM/SVG 渲染（无需 Canvas）                      |
|  - WebSocket 连接后端；两步交互（选料 → 选行）                     |
+--------------------------------+---------------------------------+
                                 | WebSocket + 少量 REST
+--------------------------------v---------------------------------+
|                       Python Backend (FastAPI)                   |
|  - Game Manager：内存中管理对局（PvP 热座 / PvE / EvE）           |
|  - Quadro Engine：纯 Python，紧凑数组状态，确定性种子             |
|  - AI Service：Random / Greedy / Minimax / MCTS，异步执行         |
+------------------------------------------------------------------+
                                 ^
                    另有 CLI 直连引擎（cli.py / benchmark.py）
```

**依赖原则**：`engine` 零第三方依赖；`ai` 只依赖 `engine`；`app` 依赖两者；CLI 工具直连 `engine`，不经服务端。前端只与 JSON 协议对话。

### 2.1 对战模式

| 模式 | 玩家 1 | 玩家 2 | 实现 |
|------|--------|--------|------|

| PvE | 人类 | AI（可选难度） | WebSocket 即时响应，AI 决策 < 500ms |

## 4. AI 分级（概要）

- **Level 0 Random**：均匀随机合法动作，基线与测试对照。
- **Level 1 Greedy**：一步模拟 + 共享评估函数取最优。
- **Level 2 Minimax + α-β**：轮内为纯完美信息博弈，深度 3~5 交替搜索，Greedy 分数做走法排序。
- **Level 3 确定化 MCTS**：UCT；跨轮时对洗袋结果采样确定化；rollout 用轻量 Greedy；预算 500ms。

详见 [03-ai.md](docs/plans/03-ai.md)。

## 5. 路线图（v3 — 垂直切片优先）

**核心原则：每个阶段结束时，你都能亲手玩到当前成果并判断对错。**

| 阶段 | 周期 | 交付 | 你能验证什么 | 出口条件 |
|------|------|------|-------------|----------|
| **P1 引擎 + CLI** | Day 1-3 | `engine/` + `scripts/cli.py`（终端可玩，ASCII 棋盘） | **终端里完整打一局**，逐步核对计分、先手标记、溢出、洗袋是否符合规则 | 全部边界判例单测通过；1000 局随机自对战不变量无违反；同种子完全可复现；**你人工打完 ≥1 局确认规则正确** |
| **P2 可玩切片** | Day 4-6 | 最小 FastAPI + 最小 Web UI（PvE 对 Random/Greedy） | **浏览器里打一局**，验证交互手感与协议 | 浏览器完整跑通 PvE 一局；非法动作被拦截；协议文档成型 |
| **P3 AI 分级** | Day 7-9 | Greedy → Minimax → MCTS，逐个落地并接入网页；`benchmark.py` | **每级 AI 落地当天你就能在网页上打它**，主观判断棋力，再对照胜率数据 | 胜率矩阵达标（见 03 号计划）；每步 < 500ms；**你主观确认难度梯度合理** |
| **P4 完整前端** | Day 10-12 | 动画、落点预览、动作日志、EvE 观战、热座 PvP、终局弹窗 | 完整产品手感 | 三模式全流程顺畅；验收清单逐条通过 |
| **P5 联调与回放** | Day 13-14 | 对局记录导出/回放校验、README、CI | 导出对局并重放 | 记录可导出且重放一致；一条命令跑全部测试 |

**关键变化**：AI 不再是最后才验证的黑盒。P3 里三级 AI 是**串行落地**的——Greedy 做完立刻接进 P2 的网页让你打，觉得太弱/太怪就当场调评估函数，再进 Minimax。评估函数的权重调参靠"你的主观棋感 + benchmark 胜率"双通道反馈，比纯数据调参可靠得多。
